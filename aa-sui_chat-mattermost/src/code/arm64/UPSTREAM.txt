Why baked into image: TE binary ships with ZERO plugins; volume-mounting
/mattermost/plugins over the image dir shadows the baked plugin. So both
plugin volumes (/mattermost/plugins + /mattermost/client/plugins) are
NOT mounted on chat-mattermost — the image IS the source of truth for
which plugins are installed.

Update procedure for the plugin:
  1. Bump v2.3.0 → new release in this file.
  2. Update build.json#docker.build_args.MM_PLUGIN_AGENTS_URL.
  3. Push → Ship → new image carries the new plugin version.

The Dockerfile takes `--build-arg MM_PACKAGE=<tarball-URL>` to control which
Mattermost binary tarball is installed. We override at build time to point at
the arm64 tarball:

  https://releases.mattermost.com/11.7.2/mattermost-team-11.7.2-linux-arm64.tar.gz

Updating the version
--------------------
  1. Pick the new tarball (mattermost-team-{V}-linux-arm64.tar.gz exists for
     11.7.0, 11.7.1, 11.7.2 — 11.7.x ESR supported through 2027-05-15).
  2. Update build.json#docker.build_args.MM_PACKAGE.
  3. Update container.app.image tag in build.json (informational).
  4. Re-fetch this Dockerfile + passwd from the matching upstream tag if a
     newer branch is being targeted; otherwise the existing Dockerfile is
     reusable for any 11.7.x patch (the version is baked only into MM_PACKAGE).
  5. Bump commit_sha + commit_at + fetched_at above; commit + push; GHA fires
     `ship-oci-apps.yml` which builds on cloud-builder (native arm64) and
     pushes to ghcr.io/diegonmarcos/chat-mattermost.

Drift policy
------------
Keep the Dockerfile byte-identical to upstream below the vendored banner.
Any local drift hides upstream security patches.
